## ADR-001 · 限流采用「先放行、后付费」，不做预扣回补

**背景**

token 级限流需要在请求进入时判断"还有没有配额"。但**一次请求会消耗多少 token，
在请求进来时是未知的** —— 输入侧可以估算，输出侧（completion）只有上游返回后才知道。

两条路：

| 方案 | 做法 |
|---|---|
| **A. 先放行、后付费** | 进入时只读判断余额；拿到上游真实 `usage` 后再扣减 |
| **B. 预扣回补** | 进入时按估算扣减；拿到真实 `usage` 后回补差额 |

**决策：选 A。**

**理由（两条，第二条是决定性的）**

1. **B 并不解决窗口末尾超额。**
   B 只能预扣**输入侧**；返回侧必须等后续阶段补。所以窗口末尾一样会超额 ——
   **B 换不来这个收益。**

2. **B 会制造「无效请求」。**（决定性）
   在余额只剩 1% 时：

   | 请求 | 预扣估算 | 结果 |
   |---|---|---|
   | 一句 `hi` | 小 | 放行，**有输出** |
   | 一段复杂请求 | 大 | **被限流拒绝** |

   而对客户来说：**输入已经给了、token 也已经记了，却没有输出 —— 这次输入实际上是无效的。**
   **B 把"超发一点点"的风险，换成了"客户花了钱没拿到东西"的确定性伤害。**

> **真正的结论**：选 A 不是技术约束的结果，是**产品取舍** ——
> **宁可窗口末尾超发一次，也要保证客户在接近配额上限时仍然可用。**
> 优化的目标不是"限流精确"，而是"客户体验"。

**代价（已知并接受）**

- 窗口末尾会超发一次（约 1 个请求的量）；
- 配额是"软上限"，不是硬上限；
- ⚠️ **事后计量的消费记录若只在内存 / 未提交阶段，进程崩溃会让那部分消费凭空消失** ——
  即"客户白嫖"。这是本方案的真实缺陷，不是理论顾虑。
  **缓解**：`Commit` 必须写进一个有 WAL / 先落盘再异步聚合的存储；本仓库的最小实现用内存，
  **并在文档与指标里显式暴露这个丢失窗口**，而不是假装它不存在。

> 📌 本项目把「预扣」与「事后计量」**两种模式都实现出来并做可测量对比**（见 README Tier 1 #2），
> 因为这条取舍的结论依赖具体约束（配额硬度 / 崩溃容忍度 / 客户体验权重），
> 没有一个放之四海皆准的答案。

**在接口上的体现**：`ratelimit.Limiter` **只有 `Check` 与 `Commit`，没有 `Reserve` / `Refund`**。
这不是遗漏，是把决策编码进接口。

## ADR-002 · 路由只做加权随机，不做自适应

**背景**

成熟网关常见 6 类选路策略：加权随机、按 token 数、按模型名、按意图、
**按延迟（汤普森采样 / P2C + EWMA）**、**按前缀亲和（radix tree，复用 KV Cache）**。

**决策：最小版只做加权随机 + 失败降级。**

**理由**

延迟类策略在真实实现里都需要**三个补丁**才能工作：

1. 冷启动守门（观测次数不足时不参与）
2. 未知后端兜底时延
3. 惩罚延迟（把持续失败的后端推入末位，防"静默过期"死锁）

**这三个补丁本身说明同一个问题**：样本量不足时，自适应策略比加权随机**更糟**。
最小版跑 demo 那点流量**永远处于冷启动**，自适应只会放大噪声。

> 所以不是"做不到"，是"**在样本量不足的前提下，复杂策略的期望收益为负**"。

**若要做**（后续）：需要先解决"冷启动阶段退化到什么" ——
可选方案是"前 N 次纯加权随机，达到阈值再切换"。

## ADR-003 · 固定窗口，而非滑动窗口

**决策**：先做固定窗口。

**已知缺陷（有意保留）**：固定窗口在**窗口边界**会出现双倍突发 ——
窗口末尾用满配额后，下一个窗口立刻又能用满，交界处瞬时速率可达配额两倍。

**为什么先接受**：实现与存储成本低，且这个缺陷是**能被讲清楚的**。
滑动窗口留作对比项 —— 知道自己简化了什么，比假装没有缺陷更重要。

## ADR-004 · 协议适配走 IR，而非两两转换

**决策**：所有协议先归一成中间表示（IR），再按目标协议序列化。

**理由**：两两转换需要 **N×(N−1)** 个转换器；IR 只需要 **N 个 Codec**。

**代价**：IR 必须足够表达所有协议的语义。已知的差异点：

| 维度 | OpenAI | Anthropic |
|---|---|---|
| 系统提示 | `role=system` 消息 | **顶层 `system` 字段** |
| 结束原因 | `finish_reason` | **`stop_reason`** |
| 思考预算 | `reasoning_effort` | **`thinking.budget_tokens`** |
| 流式 | 统一 `data:` 帧 | **多事件类型** |
| 工具调用 | `tool_calls` | **`tool_use` / `tool_result` 内容块** |

## ADR-005 · 明确不做的东西

| 不做 | 理由 |
|---|---|
| 语义缓存 | 需要向量库 + 相似度阈值 + token 距离校验；**误命中代价极高**（答错比不快更糟） |
| MCP / A2A 接入 | 属于产品能力，不是网关内核 |
| 内容安全（敏感词 / 提示词防护） | 需要多路检测，属旁路能力 |
| 预扣回补 | 见 ADR-001 |

> 列出"不做什么"和列出"做什么"同样重要 ——
> 它界定了这个项目是一个**可读完的最小实现**，而不是又一个半成品网关。

## ADR-006 · 为什么把 scope 从"通用网关 + LLM"改成"AI 网关的内核"

**背景**

初版 scope 是：协议转换 / SSE 流式 / token 限流 / 多上游路由 /（加分）成本统计 /（加分）语义缓存。

**问题**：这四项里，**「流式」「限流」「路由」是任何通用 API 网关都有的** —— 只是加了 LLM 味道。
照这个 scope 做出来，是一个"能代理 LLM 的 API 网关"，不是一个 AI 网关。

**决策：按「围绕 token 的经济性」重定 scope。**

| | 通用 API 网关管什么 | AI 网关管什么 |
|---|---|---|
| 核心对象 | **请求**（QPS、连接数、状态码） | **token 与钱**（用量、成本、缓存折扣） |
| 限流维度 | QPS / 并发 | **token 数 / 预算 / 虚拟 Key 余额** |
| 缓存 | 可选，为了性能 | **核心，且要算得清盈亏**（读 0.1× vs 写 1.25–2×） |
| 路由依据 | 权重 / 健康度 | **模型单价**（同一任务不同模型成本可差 100×） |
| 计费 | 不涉及 | **必须**（否则客户与厂商都对不上账） |

**依据**（对标 180+ 网关的公开清单）：
- 这些维度在通用网关里**根本不存在**，是 AI 网关独有的；
- 其中两项被列为独立章节：**「并发下预扣与事后计量的区别」**、**「缓存经济学：命中率低于 ~21.7% 时开缓存反而亏钱」**；
- 还有一条容易被忽略：**多数账单里最大的一笔没领的折扣，是网关悄悄破坏了上游的 prompt caching**。

**后果**

- 限流从"核心能力"降级为"计量的一个应用"；
- **计量 / 预算 / 虚拟 Key** 与 **缓存经济学** 升为核心必做；
- 路由从"加权随机"升级为"成本感知"。

> 记录这条 ADR 的原因：**scope 定错比实现做错更贵** ——
> 做完了才发现做的不是这个东西，返工成本是整个项目。
